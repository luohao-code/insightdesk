## 3 协作规范

### 3.1 分支模型

```text
main                稳定分支，始终可运行、可演示
 └─ develop         集成分支
     ├─ feature/backend-*
     ├─ feature/frontend-*
     └─ feature/engine-*
```

- 每个功能在独立分支开发，完成后通过 Pull Request 合入 `develop`；
- 杨文杰（小组长）负责最终审查与合入 `main`；
- 阶段交付时在 `main` 打标签：`v0.1-phase1`、`v0.5-phase2`、`v1.0`。

### 3.2 提交信息规范

采用 Conventional Commits 的简化版：

```text
<type>(<scope>): <subject>

type: feat | fix | docs | style | refactor | test | chore | perf
scope: backend | frontend | ocr | ai | web | export | desktop | docs
```

示例：

```text
feat(backend): 新增批量任务队列与失败重试
feat(frontend): 实现 OCR 工作台拖拽上传与结果编辑
docs(docs): 完成阶段一进展报告与需求规格说明书
```

### 3.3 代码评审清单

1. 是否满足对应需求编号，是否有验收方式；
2. 异常路径是否处理（超时、空数据、非法输入）；
3. 是否存在密钥、绝对路径、调试输出等敏感信息；
4. 前端是否存在 `innerHTML` 拼接用户输入（XSS 风险）；
5. 新增接口是否有测试覆盖；
6. 命名与注释是否清晰，是否存在重复逻辑。

### 3.4 沟通与节奏

| 活动 | 频率 | 参与人 | 产出 |
| --- | --- | --- | --- |
| 站会 | 每周一/四，15 分钟 | 全体 | 进展、阻塞、当日计划 |
| 需求评审 | 阶段一初 | 全体 | 评审结论、需求基线 |
| 设计评审 | 阶段一末 | 全体 | 设计文档、接口契约 |
| 代码评审 | 每次 PR | 至少 1 人 | 评审意见 |
| 阶段复盘 | 每阶段末 | 全体 | 阶段进展报告 |

### 3.5 文档与资产管理

- 文档统一放在 `docs/`，命名以序号开头，便于排序；
- 接口变更必须同步更新 `docs/03-详细设计说明书.md` 的接口章节；
- 用户数据、密钥、日志不进入版本库（见 `.gitignore`）；
- 进度报告按阶段归档至 `docs/进展报告/`。

## 5 贡献度说明

本项目为课程团队项目，三名成员均参与实际开发与文档编写。贡献度按工作量与关键程度综合评估：

- 杨文杰：35%（项目负责人 / 小组长，项目统筹、前端与交互、评审与发布）
- 罗浩：35%（架构与后端负责人，架构、后端核心、集成与报告）
- 邹俊杰：30%（引擎适配、测试、文档与打包）

以上分工同时记录于各阶段进展报告，作为课程过程性考核依据。
