# AI 生成式开发经验分享

**项目**：识文台 InsightDesk
**撰写**：罗浩、杨文杰、邹俊杰
**日期**：2026-11-10

---

## 1 背景

课程要求"探索利用 AI 进行生成式软件开发，并探索如何让 AI 高质量完成各项软件开发任务"。本项目从需求分析到编码、测试、文档，全流程使用了 AI 辅助，但仍由三名成员对架构、安全与质量负责。

**核心结论**：AI 能显著提升"从想法到可运行代码"的速度，但**不能替代需求判断、架构取舍与验证**。高质量来自"明确约束 + 小步生成 + 自动验证 + 人工评审"的闭环。

## 2 我们如何使用 AI

| 阶段 | AI 承担 | 人工承担 |
| --- | --- | --- |
| 需求 | 竞品梳理、需求条目化、验收标准草稿 | 范围裁剪、优先级、排除项决策 |
| 设计 | 架构备选、接口契约草稿、数据字典 | 技术选型、并发模型、安全边界 |
| 编码 | 模块骨架、适配器、组件、测试用例 | 关键算法、并发修复、代码审查 |
| 测试 | 用例生成、边界条件补充 | 真实环境验证、缺陷定位 |
| 文档 | 手册初稿、报告结构 | 事实核对、数据校准、团队分工 |

## 3 有效的提示词模式

### 3.1 角色 + 上下文 + 约束 + 输出格式

```text
你是资深 FastAPI 工程师。项目使用 Python 3.12 + SQLAlchemy 2.0 + SQLite。
请实现批量任务服务，要求：
1. 每批次一个线程池，并发 1–8；
2. 失败按指数退避重试，次数可配置；
3. 计数必须原子更新，避免并发丢失；
4. 通过事件总线推送进度；
5. 只输出完整文件，不要省略。
```

**效果**：一次生成可用骨架，减少来回。

### 3.2 先约束接口，再让 AI 填实现

先手写 Pydantic Schema 与路由签名，再让 AI 实现服务层。这样前端、后端、测试可以并行，AI 也不容易"发明"不存在的字段。

### 3.3 让 AI 自检与互相审查

- 生成后要求"列出 5 个可能的边界条件并补充测试"；
- 对关键模块要求"指出这段代码在并发/异常/安全上的风险"；
- 用另一个会话审查同一段代码，减少自洽性偏差。

### 3.4 用真实运行结果反哺提示词

例如批量计数缺陷，把失败现象、复现步骤、期望结果交给 AI，要求"只分析根因，不写代码"，确认根因后再要求最小修复。比直接说"帮我修 bug"更可靠。

## 4 质量控制

1. **自动验证优先**：每生成一个模块，立即运行 pytest 与 `node --check`；
2. **真实引擎验证**：安装 RapidOCR 对示例图识别，避免"演示引擎通过即认为 OCR 可用"；
3. **浏览器走查**：用自动化浏览器检查页面渲染、导航与控制台；
4. **安全复核**：SSRF、密钥、路径穿越、XSS、CSV 注入逐项检查；
5. **代码规模与结构**：用脚本统计行数，但拒绝为凑行数写无意义代码；
6. **人工评审清单**：异常路径、敏感信息、重复逻辑、命名与注释。

## 5 踩过的坑

| 坑 | 表现 | 教训 |
| --- | --- | --- |
| 幻觉 API | 生成了不存在的库函数/参数 | 先查官方文档，再用最小示例验证 |
| 并发丢失更新 | 内存 `+1` 写回，计数偏少 | 计数类操作必须用数据库原子更新 |
| 过度合并 | OCR 标题与正文粘连 | 启发式规则需要真实样本回归 |
| 缓存干扰 | 改了 CSS 但浏览器仍旧样式 | Service Worker 版本化，网络优先 |
| 只测演示引擎 | 以为 OCR 已完成 | 必须用真实引擎跑一遍样例 |
| 密钥泄漏风险 | 示例代码把 Key 写在配置里 | 统一服务端存储 + 掩码 + CI 扫描 |
| 为规模而规模 | 生成大量重复模板 | 以功能和可维护性为先，规模是结果 |

## 6 三人协作中的 AI 使用

- **杨文杰（小组长）**：用 AI 生成组件骨架与 CSS，人工把控设计系统、交互细节与响应式，并负责整体进度与评审；
- **罗浩**：用 AI 生成架构备选与接口草稿，重点人工设计任务队列、SSRF 防护与并发一致性；
- **邹俊杰**：用 AI 生成引擎适配与测试用例，人工核对签名算法、真实 OCR 与导出文件可用性。

协作约定：

1. 每个 PR 描述中注明"哪些由 AI 生成、哪些人工修改"；
2. AI 生成的代码必须通过测试与评审才能合并；
3. 文档中的数字（行数、用例数、耗时）必须来自实际运行结果。

## 8 建议

1. **先想清楚再让 AI 写**：需求边界、数据模型、接口契约是最值得人工投入的部分；
2. **小步生成、频繁验证**：一次生成一个模块，立即运行测试；
3. **让 AI 解释，不只让 AI 产出**：要求它说明取舍与风险；
4. **真实数据验证**：演示数据、Mock 引擎只能验证流程，不能验证能力；
5. **保留人的判断**：安全、隐私、并发、用户体验的最终责任在团队。

## 9 示例：一次高质量的修复对话

```text
现象：3 张图片的批次偶尔显示成功 2/3，但批次状态为 succeeded。
期望：成功数必须等于 3。
约束：不改变接口，不引入新依赖。
请先分析根因，给出 2 种修复方案及取舍，暂不写代码。
```

确认"多线程读改写导致丢失更新"后，再要求：

```text
采用数据库原子自增方案，修改成功/失败计数；补充一个并发回归测试；
说明修改点与验证方式，只输出 diff。
```

这种"先诊断、再决策、最后最小修改"的流程，比一次性让 AI 重写整个模块更可控。

---

**一句话总结**：AI 是加速器，不是驾驶员。把需求、架构与验证握在自己手里，才能真正"高质量"。
